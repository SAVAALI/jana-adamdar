# Подключение общей базы

Новый проект: `https://tpmhqzqfudcsdzfdhfjc.supabase.co`.
Публичный ключ находится в `config.js`. В браузере не используются пароль базы, `service_role` или secret key.

## 1. Создать таблицы и хранилище

В **новом проекте jana-adamdar** откройте **SQL Editor → New query**. Скопируйте весь файл [`setup.sql`](setup.sql) и нажмите **Run**. Ожидаемый результат — `Success. No rows returned`.

Скрипт создаёт только объекты с префиксом `vsg_` и приватное хранилище `vsg-report-photos`. Он не содержит демонстрационных магазинов, не удаляет существующие отчёты и поддерживает повторный запуск. Автоматическое открытие новых таблиц в настройках проекта можно оставить выключенным: необходимые права выдаются явно.

## 2. Настроить ссылки из писем

В **Authentication → URL Configuration** установите:

- **Site URL:** `https://savaali.github.io/jana-adamdar/`
- **Redirect URLs:** добавьте `https://savaali.github.io/jana-adamdar/`.

Для проверки на компьютере можно отдельно добавить фактический адрес локального сервера в Redirect URLs. Не отключайте подтверждение почты ради обхода настройки писем.

Для писем участникам вне организации потребуется настроить **Authentication → Email / SMTP**: встроенная почта Supabase имеет ограничения адресатов и частоты. Для первого входа владельца используйте подтверждённую почту, разрешённую настройками вашего проекта. Пароли SMTP вводятся только в настройках Supabase.

## 3. Включить общую базу на сайте

После успешного выполнения SQL измените в `config.js` только `enabled: false` на `enabled: true` и отправьте изменение в `main`. Публикация GitHub Pages обновит сайт. Демо-записи не переносятся в общую базу. Локальные отчёты прототипа остаются в IndexedDB и не удаляются.

До этого переключения опубликованный прототип продолжает работать. После переключения при недоступности базы сайт показывает ошибку загрузки; он не подменяет реальные отчёты демонстрационными.

## Обновление существующего проекта: настоящая карта

В SQL Editor выполните [`real-map.sql`](real-map.sql). Для новых проектов координаты уже включены в полный `setup.sql`. Скрипт добавляет широту и долготу проверки и две функции; данные и статусы сохраняются, повторный запуск допустим.

- В форме отчёта нажмите **Выбрать место на карте**. Найдите адрес, выберите результат, проверьте здание и подтвердите точку. Можно поставить метку вручную и перетащить её. Координаты в Астане сохраняются атомарно с отчётом через `vsg_submit_located_report`; публикация остаётся отдельным действием администратора.
- Для уже существующих проверок администратор открывает **Кабинет → Проверка отчётов → Указать место на карте**. После подтверждения координаты сохраняются через `vsg_set_report_location`. Только администратор может корректировать место уже отправленного отчёта.
- Отчёты без координат доступны в списке; их положение не выдумывается. Отчёт без точки по-прежнему можно отправить и опубликовать. Последняя опубликованная проверка определяет позицию магазина на карте.
- До выполнения миграции старый путь отправки и чтения работает. Сохранение координат покажет понятную ошибку с именем нужного SQL-скрипта; фото и форма сохраняются для повторной попытки.
- Leaflet 1.9.4 и его CSS хранятся локально. Подложка — OpenStreetMap; атрибуция всегда видна. Публичный Photon используется только по кнопке поиска, результаты ограничены Астаной и подтверждаются пользователем. Нет массового геокодирования, слежения за геопозицией или автоматического размещения адресов.
- Карта требует доступа к `tile.openstreetmap.org`, поиск — к `photon.komoot.io`. Это внешние публичные сервисы без гарантии доступности; при сбое поиска точку можно выбрать вручную. При недоступности подложки отчёты остаются в списке. В этой облачной среде прямые запросы к обоим доменам блокируются прокси (403); карта, сохранение и ошибки проверены в Chromium с тестовым HTTP API и тестовыми тайлами. Реальную загрузку подложки нужно проверить в браузере пользователя.

## История опубликованных проверок

В существующем проекте выполните [`history.sql`](history.sql) в SQL Editor. Скрипт создаёт только безопасное публичное представление `vsg_public_history`, не меняет отчёты и допускает повторный запуск. Он не зависит от миграции координат. Для новой базы достаточно полного `setup.sql`.

В истории показаны все опубликованные проверки выбранного магазина в порядке `occurred_at`, `created_at`, `id` по убыванию. Загружаются страницы по 20 записей, дополнительные страницы — по кнопке. Записи на проверке и отклонённые отсутствуют даже при просмотре публичной истории администратором. Автор, email, внутренние замечания и исходные имена файлов не включены. После снятия с публикации запись исчезает из последующих запросов истории; ранее выданные подписанные ссылки на фото действуют до истечения своего часа. Новое представление, как и публичная карта, выполняется с правами владельца и имеет `security_barrier` с явным фильтром публикации; изменение данных через него запрещено.

Черновики не требуют SQL: они хранятся в IndexedDB в браузере, отдельно для каждого аккаунта и проекта. На один аккаунт на этом устройстве предусмотрен один текущий черновик. После выхода форма очищается; при возвращении к аккаунту восстанавливается его черновик. Это локальное сохранение, не серверный доступ к чужим отчётам. После подтверждённой отправки черновик и его локальные фото удаляются. Для прерванной отправки сохраняется ID попытки; повтор после перезагрузки использует тот же ID и те же пути фото. При смене аккаунта незавершённая отправка останавливается до следующего запроса.

## 4. Назначить первого администратора

1. На сайте нажмите **Войти → Создать аккаунт** и зарегистрируйтесь со своей почтой.
2. Подтвердите почту по ссылке из письма и войдите. Аккаунт сначала имеет статус **Ожидает доступа**.
3. В [`make-admin.sql`](make-admin.sql) замените `ВАША_ПОЧТА` своей подтверждённой почтой и выполните файл в **SQL Editor** этого проекта.
4. На сайте нажмите **Обновить кабинет**. Появятся разделы проверки отчётов и управления участниками.

Скрипт выдаёт права только найденному подтверждённому аккаунту с указанной почтой. Первый зарегистрировавшийся пользователь не получает права автоматически. Остальных участников администратор разрешает в кабинете; выдача дополнительных административных прав выполняется через SQL Editor.

## Как работают данные и доступ

- Гости видят только последнюю одобренную проверку каждого магазина и общие показатели по одобренным отчётам.
- Участник после одобрения аккаунта может отправлять отчёты. Магазин, отчёт и метаданные фото сохраняются одной транзакцией после загрузки файлов.
- Новые отчёты имеют статус `pending`. Автор видит свои отчёты и комментарии администратора. Другие участники не видят чужие неопубликованные проверки.
- Администратор может одобрить или отклонить отчёт, снять его с публикации, разрешить или приостановить доступ участника.
- Файлы находятся в **приватном** bucket. Подписанные ссылки выдаются только для доступных конкретному посетителю фотографий и действуют один час. Уже выданная ссылка может работать до истечения этого срока, даже если отчёт снят с публикации.
- Все проверки ролей повторяются в SQL/RLS. Изменение интерфейса или публичного ключа не даёт административных прав. Прямые изменения таблиц через клиентский API запрещены; запись идёт через проверяемые функции `vsg_*`.
- Публичные представления намеренно выполняются с правами владельца и фильтруют только одобренные записи. Они не включают адреса почты, исходные имена файлов и внутренние комментарии. Это может отображаться как уведомление о Security Definer View в Supabase Advisor; состав полей и фильтр проверяются тестом `npm test`.
- Карта обновляется раз в минуту, при возвращении на вкладку и кнопкой **Обновить карту**. В режиме общей базы используется настоящая карта OpenStreetMap; координаты указываются участником или администратором, адрес можно найти через Photon.
- Сбой отправки сохраняет форму и фотографии на экране. Повторная попытка той же формы использует прежний ID отчёта и не создаёт дубликат. Неотправленная форма и фото автоматически сохраняются на устройстве и восстанавливаются после перезагрузки; состояние сохранения показано над формой. Не привязанные к отчёту файлы после сетевого сбоя остаются приватными; их можно удалить при обслуживании Storage.

## Проверка после подключения

1. Зарегистрируйте участника, подтвердите почту и разрешите доступ из кабинета администратора.
2. Отправьте один отчёт с фото. В кабинете автора он должен иметь статус **На проверке**, а в отдельном окне без входа — отсутствовать.
3. Администратор открывает фото и нажимает **Опубликовать**. В другом браузере нажмите **Обновить карту**: должна появиться новая точка, описание и фото.
4. Снимите отчёт с публикации и убедитесь, что точка исчезла после обновления (если у магазина нет другой одобренной проверки).

В облачной среде прямой запрос к домену проекта сейчас блокируется прокси (403). Для проверки из этой среды разрешите `tpmhqzqfudcsdzfdhfjc.supabase.co` в её сетевых настройках. Браузер посетителя GitHub Pages использует свою сеть.

SQL и политики проверены локально в PostgreSQL через PGlite. Клиент с официальным Supabase SDK проверен в Chromium с тестовым HTTP API. Эти проверки не подтверждают выполнение SQL и доставку писем в вашем реальном проекте — их нужно проверить после шагов выше.
